# Отчёт по практической №1 — Lakehouse на Iceberg

## 1\. Вариант и масштаб

| Поле | Значение |
| :---- | :---- |
| ФИО (как в VK Education) | Арюзин Никита Сергеевич |
| Вариант (запрос) | TPC-H Q10 — клиенты с наибольшей выручкой по возвращённым товарам за IV квартал 1993 года |
| Масштаб `sfN` | `sf1` |
| Почему выбран такой масштаб | В `lineitem` около 6 млн строк, поэтому можно проверить JOIN, фильтрацию и агрегацию на достаточно большом наборе. `sf1` при этом подходит для локального Docker-стека и не требует отдельного сервера. |

## 2\. Поднятые сервисы — и почему именно они

| Сервис | Роль в стеке | Почему выбран |
| :---- | :---- | :---- |
| S3-совместимое хранилище (`pgsty/silo:latest`) | Хранение Parquet-файлов и метаданных Iceberg; API `9000`, веб\-консоль `9001` | Локальная замена облачному S3: файлы хранятся отдельно от SQL-движка и каталога. |
| PostgreSQL 17 | База метаданных Lakekeeper; порт хоста `5433` | Хранит служебные данные каталога, а не аналитические Parquet-таблицы. Внутри Docker-сети PostgreSQL доступен на `postgres:5432`. |
| Lakekeeper 0.13.1 | REST-каталог Apache Iceberg; порт `8181` | Управляет схемами, расположением таблиц и снапшотами Iceberg. Trino обращается к нему через REST API. |
| Trino 476 | SQL-движок; порт `8080` | Выполняет CTAS, JOIN и агрегации; каталог `tpch` предоставляет исходные таблицы `sf1`, а каталоги Iceberg обращаются к Lakekeeper и S3-хранилищу. |
| Apache Superset 6.0.0 | BI-интерфейс; порт `8088` | Подключается к Trino через Python-пакет `trino[sqlalchemy]`, читает Iceberg-таблицы через SQL и позволяет строить чарты и дашборды по Gold без копирования данных. |
| DBeaver | Клиент для запуска SQL | Удобен для последовательного выполнения скриптов и проверки результатов запросов Trino. |

&nbsp;

### Скрипт запуска

Конфигурация сервисов и каталоги Trino находятся в `docker-compose.yml` и папке `catalog/`. Для запуска из PowerShell:

```powershell
cd D:\vkdata\seminariki\lakehouse
docker volume create minio-data
docker volume create pg-data
docker compose up -d --build
docker compose ps
```

&nbsp;

Перед запуском Superset в корне проекта создаётся `.env` со сгенерированным `SUPERSET_SECRET_KEY`; настоящий ключ не записывается в исходный код и не публикуется в репозитории. Для его чтения в `docker-compose.yml` переменная передаётся контейнеру, а `superset_config.py` загружает её через `os.environ`. Файл `.env` должен быть исключён в `.gitignore`.

При первом запуске Superset инициализируется отдельно:

```powershell
docker compose exec superset superset db upgrade
docker compose exec superset superset init
```

&nbsp;

Метабаза Superset использует SQLite в `/app/superset_home/superset.db`; для сохранения настроек после пересоздания контейнера путь `/app/superset_home` должен быть подключён к постоянному именованному тому, например `superset-data`. Не выполняй `docker compose down -v`, если требуется сохранить дашборды и настройки.

Основной SQL-конвейер находится в `queries/TPC_H_Q10.sql`; вариант с явным `ZSTD` — в `queries/TPC_H_Q10_ZSTD.sql`. Скрипты выполняются по порядку через одно подключение к Trino (`localhost:8080`). Веб-интерфейсы: S3-консоль `http://127.0.0.1:9001`, Superset `http://localhost:8088`.

## 3\. Разбор запроса — какие данные нужны

Запрос формирует рейтинг 20 клиентов по чистой выручке от возвращённых товаров. Учитываются заказы с `1993-10-01` включительно до `1994-01-01` не включительно и строки `lineitem`, для которых `returnflag = 'R'`.

| Таблица TPC-H | Нужные колонки | Использование |
| :---- | :---- | :---- |
| `customer` | `custkey`, `name`, `acctbal`, `nationkey`, `address`, `phone`, `comment` | Ключ соединения и атрибуты клиента для итоговой витрины. |
| `orders` | `orderkey`, `custkey`, `orderdate` | Соединение с клиентом и позициями заказа; фильтр по IV кварталу 1993 года. |
| `lineitem` | `orderkey`, `linenumber`, `partkey`, `suppkey`, `quantity`, `extendedprice`, `discount`, `returnflag` | Соединение с заказами, фильтр возврата и расчёт `extendedprice * (1 - discount)`. |
| `nation` | `nationkey`, `name` | Соединение по стране клиента и вывод названия страны. |

## 4\. Медальон — решения по слоям

Таблицы записываются в Iceberg в формате `PARQUET`. В рабочем варианте для слоёв используется `ZSTD`; партиционирование не задано, поскольку для `sf1` оно усложнило бы конфигурацию и могло бы создать много мелких файлов. Размеры файлов и количество строк Silver ниже приведены как реалистичные оценки; точные значения проверяются через `COUNT(*)` и метаданные таблиц.

### Bronze (сырой слой)

| Таблица | Колонки | Строк | Вес, МБ (≈) | Формат | Сжатие | Партиционирование | Обоснование |
| :---- | :---- | ----: | ----: | :---- | :---- | :---- | :---- |
| `customer` | Все исходные колонки | 150 000 | 8 | PARQUET | ZSTD | Нет | Полная исходная копия для повторной обработки без повторного обращения к генератору TPC-H. |
| `orders` | Все исходные колонки | 1 500 000 | 50 | PARQUET | ZSTD | Нет | Сохраняются исходные заказы; фильтр по дате применяется на Silver, чтобы Bronze оставался переиспользуемым. |
| `lineitem` | Все исходные колонки | 6 001 215 | 222 | PARQUET | ZSTD | Нет | Самая крупная таблица; Parquet и сжатие уменьшают размер хранения и объём чтения. |
| `nation` | Все исходные колонки | 25 | \<0,1 | PARQUET | ZSTD | Нет | Маленький справочник; разбиение на партиции не даст заметного эффекта. |

&nbsp;

### Silver (очищенный слой)

| Таблица | Колонки | Строк (≈) | Вес, МБ (≈) | Формат | Сжатие | Партиционирование | Обоснование |
| :---- | :---- | ----: | ----: | :---- | :---- | :---- | :---- |
| `returned_items` | `custkey`, `name`, `acctbal`, `nation`, `address`, `phone`, `comment`, `orderkey`, `orderdate`, `linenumber`, `partkey`, `suppkey`, `quantity`, `extendedprice`, `discount`, `returnflag`, `line_revenue` | 50 000–55 000 | 4 | PARQUET | ZSTD | Нет | Выполняются JOIN четырёх таблиц, фильтр дат и `returnflag = 'R'`, удаляются строки с отсутствующими ключами/суммами, текст нормализуется через `TRIM`/`NULLIF`; рассчитывается `line_revenue`. |

&nbsp;

### Gold (витрина)

| Таблица | Колонки | Строк | Вес, МБ (≈) | Формат | Сжатие | Партиционирование | Обоснование |
| :---- | :---- | ----: | ----: | :---- | :---- | :---- | :---- |
| `top20_returned` | `custkey`, `name`, `revenue`, `acctbal`, `nation`, `address`, `phone`, `comment` | 20 | \<0,1 | PARQUET | ZSTD | Нет | Агрегирует выручку по клиентам и хранит 20 лидеров. Небольшую витрину удобно читать в Superset; партиционирование не требуется. |

&nbsp;

Количество строк Bronze соответствует кардинальностям TPC-H `sf1`. Для проверки количества записей Silver и Gold скрипт включает `COUNT(*)`; для точного размера файлов используется таблица Iceberg `"table$files"`.

## 5\. Тесты производительности

### Методика

Для сравнения кодеков используется одна и та же таблица `tpch.sf1.orders` (1 500 000 строк, все колонки), формат `PARQUET` и одинаковые версии сервисов. В контрольном прогоне перед созданием таблицы явно задаётся `SET SESSION bronze.compression_codec = 'GZIP'`; второй вариант использует `ZSTD` из `TPC_H_Q10_ZSTD.sql`. Кодек меняется только для Bronze, а обработка Silver/Gold остаётся одинаковой. Размер записанных файлов определяется через `sum(file_size_in_bytes)` из `bronze.lakehouse."orders$files"`.

Архив содержит SQL-сценарии, но не содержит журналов хронометража и экспорта размеров файлов. Поэтому приведённые ниже цифры — **ориентировочные значения для локального Docker-стенда**, а не подтверждённые замеры сохранённого лога.

| Профиль | Время записи `orders`, с (≈) | Размер `orders`, МБ (≈) | Размер всего Bronze, МБ (≈) | Обработка Silver \+ Gold, с (≈) |
| :---- | ----: | ----: | ----: | ----: |
| PARQUET \+ GZIP | 283 | 64 | 315 | 78 |
| PARQUET \+ ZSTD | 247 | 59 | 280 | 67 |

&nbsp;

В таком сценарии `ZSTD` записывает контрольную таблицу примерно на 13% быстрее, а её размер получается примерно на 8% меньше. Оценочный общий объём Bronze уменьшается примерно на 11%. Для окончательного сравнения следует выполнить каждый профиль несколько раз на одной машине и сравнить медианы; Trino по умолчанию для Iceberg использует `ZSTD`, поэтому профиль GZIP необходимо задавать явно.

## 6\. Часть 2 — осмысление и работа с инструментами

### 6.1. Понять и объяснить

| Вопрос | Ответ |
| :---- | :---- |
| Зачем нужны большие данные и lakehouse, а не только обычная БД? | Lakehouse хранит крупные наборы файлов в объектном хранилище, а Iceberg добавляет схему, снапшоты и управление изменениями. Trino обрабатывает данные SQL-запросами без необходимости загружать весь объём в одну реляционную БД. |
| Пример schema evolution на Silver | `ALTER TABLE silver.lakehouse.returned_items ADD COLUMN processing_note VARCHAR;`. Iceberg фиксирует новую схему в метаданных; у существующих строк новое поле читается как `NULL`, а старые Parquet-файлы не требуется вручную переписывать. Это пример операции для демонстрации. |
| Пример восстановления из снапшота (time travel) | Получить ID снимков: `SELECT snapshot_id, committed_at FROM gold.lakehouse."top20_returned$snapshots" ORDER BY committed_at DESC;`. Прочитать состояние: `SELECT * FROM gold.lakehouse.top20_returned FOR VERSION AS OF <SNAPSHOT_ID>;`. Откатить текущее состояние: `ALTER TABLE gold.lakehouse.top20_returned EXECUTE rollback_to_snapshot(<SNAPSHOT_ID>);`, подставив существующий ID снимка. |

&nbsp;

### 6.2. Подключение BI-инструмента

| Инструмент | Почему выбран и как используется |
| :---- | :---- |
| Apache Superset 6.0.0 | Работает поверх уже развёрнутого Trino и не копирует данные из Lakehouse. Используется для проверки Bronze и подготовки визуализаций по Gold. В качестве источника дашборда выбрана витрина `gold.lakehouse.top20_returned`. |

&nbsp;

В `superset/Dockerfile` используется базовый образ `apache/superset:6.0.0`. Чтобы Trino был доступен из самого Superset, в виртуальное окружение образа устанавливается пакет с поддержкой SQLAlchemy:

```dockerfile
FROM apache/superset:6.0.0

USER root
RUN . /app/.venv/bin/activate && \
    uv pip install --no-cache-dir "trino[sqlalchemy]"
USER superset
```

&nbsp;

Команда `python -m pip install` в этом образе не подходит, потому что в `/app/.venv` модуль `pip` отсутствует; использован штатный `uv pip`. После пересборки образа импорт пакета `trino` был проверен, установленная версия — `0.340.0`.

В `superset_config.py` задаются английская локаль по умолчанию и словарь `LANGUAGES` с ключами `en` и `ru`. Это устранило ошибку интерфейса `Cannot read properties of undefined (reading 'flag')`. В конфигурации также используется переменная окружения `SUPERSET_SECRET_KEY`; сам секрет хранится в локальном `.env`, а не в коде проекта. Миграции метабазы были применены командами `superset db upgrade` и `superset init`, после чего синхронизация конфигурации завершилась успешно. Контейнер проходит внутреннюю проверку `/health` с HTTP 200\.

#### Подключение Trino

В Superset добавлено подключение к Trino. Для текущей Docker-сети в SQLAlchemy URI используется имя сервиса `trino`, а не `localhost`:

```
trino://trino@trino:8080/gold
```

&nbsp;

Подключение проверено через кнопку **Test Connection** и работает. Каталог `gold` содержит схему `lakehouse` с итоговой витриной. Дополнительная проверка структуры выполняется командами в SQL Lab:

```sql
SHOW SCHEMAS FROM gold;
SHOW TABLES FROM gold.lakehouse;
DESCRIBE gold.lakehouse.top20_returned;
```

&nbsp;

Для просмотра данных витрины:

```sql
SELECT custkey, name, revenue, nation, acctbal
FROM gold.lakehouse.top20_returned
ORDER BY revenue DESC;
```

&nbsp;

Запрос предполагает, что таблица `top20_returned` создана предыдущим SQL-конвейером. Если её нет, сначала следует выполнить соответствующий сценарий `queries/TPC_H_Q10.sql` через Trino и убедиться, что итоговая таблица появилась.

#### Создание Dataset, чартов и дашборда

В Superset сначала создаётся Dataset — описание таблицы, которая будет источником графиков:

1. Открыть **Data → Datasets → \+ Dataset**.  
2. Выбрать подключение к Trino, каталог `gold`, схему `lakehouse` и таблицу `top20_returned`.  
3. Нажать **Add**, затем открыть датасет через **Explore** или создать чарт из списка **Charts**.  
4. После настройки визуализации нажать **Run**, проверить результат и **Save**.

Для этой витрины можно использовать следующие виды визуализаций:

| Чарт | Поля и метрики | Что показывает |
| :---- | :---- | :---- |
| Bar Chart — «Выручка клиентов Top-20» | Категория `name`; метрика `SUM(revenue)`; сортировка по метрике по убыванию; ограничение, например, 10 строк | Сравнение выручки клиентов, уже попавших в витрину Top-20. |
| Big Number — «Выручка Top-20» | Метрика `SUM(revenue)` | Суммарная выручка по строкам витрины Top-20, а не общая выручка всего набора TPC-H. |
| Table — «Клиенты Top-20» | Колонки `custkey`, `name`, `nation`, `revenue`, `acctbal`; сортировка по `revenue` по убыванию | Детальная таблица клиентов с ключевыми показателями. |

&nbsp;

Для линейного графика по времени нужен реальный столбец даты/времени. В `gold.lakehouse.top20_returned` такого поля в описанной структуре нет, поэтому временной график следует строить только на другом датасете, содержащем дату.

Сохранённые чарты можно объединить в **Dashboards → \+ Dashboard**, например под названием `Lakehouse Analytics`. Рекомендуемая компоновка: вверху KPI-карточка, далее столбчатая диаграмма и доли по странам, внизу — таблица клиентов. Данный отчёт описывает конфигурацию и рекомендуемый порядок сборки; факт успешного подключения к Trino подтверждён, но наличие уже сохранённого пользователем дашборда не предполагается без отдельной проверки в интерфейсе.

#### Сохранение и экспорт Superset

Настройки подключений, Dataset, чартов и дашбордов записываются в метабазу Superset, а не в файлы SQL-таблиц Lakehouse. Чтобы они переживали пересоздание контейнера, метабаза `/app/superset_home/superset.db` должна находиться в постоянном Docker volume. Для создания резервной копии готовых дашбордов можно использовать CLI:

```powershell
docker compose exec superset superset export-dashboards --help
docker compose exec superset superset export-dashboards --dashboard-file /tmp/dashboards.zip
New-Item -ItemType Directory -Force .\superset\exports
docker cp lakehouse-superset:/tmp/dashboards.zip .\superset\exports\dashboards.zip
```

&nbsp;

Если название контейнера в Compose отличается, в `docker cp` следует подставить фактическое имя из `docker compose ps`. Экспорт нужно делать после создания и сохранения дашборда; пустая метабаза или отсутствие дашбордов не дадут нужной резервной копии.

Файлы конфигурации (`docker-compose.yml`, `superset/Dockerfile`, `superset_config.py`, SQL и README) можно хранить в GitHub. Перед коммитом необходимо убедиться, что `.env`, секретный ключ, пароли и локальная метабаза SQLite исключены через `.gitignore`. Архив экспортированного дашборда можно сохранить в `superset/exports/` после проверки его содержимого на конфиденциальные сведения. Сам Docker volume и данные объектного хранилища в Git-репозиторий автоматически не попадают.

## 7\. Проблемы и решения

| Проблема | Причина | Решение |
| :---- | :---- | :---- |
| Lakekeeper выдавал ошибку подключения к PostgreSQL / строку не в UTF-8 | Подключение шло не к тому порту PostgreSQL на хосте | В Compose Lakekeeper использует адрес `postgres:5432` внутри Docker-сети; порт `5433` оставлен для подключения с Windows. |
| Superset возвращал HTTP 500 с `no such table: themes` | Не были применены миграции базы метаданных Superset | Выполнены `superset db upgrade` и `superset init`; после этого синхронизация конфигурации завершилась успешно. |
| Superset показывал пустую страницу с ошибкой `reading 'flag'` | Язык интерфейса отсутствовал в словаре `LANGUAGES` | В `superset_config.py` добавлены описания `en` и `ru`, задан `BABEL_DEFAULT_LOCALE = 'en'`; после пересоздания контейнера интерфейс загрузился. |
| При сборке Superset возникало `No module named pip` | Виртуальное окружение базового образа `/app/.venv` не содержит модуль `pip` | В `superset/Dockerfile` использована команда `. /app/.venv/bin/activate && uv pip install --no-cache-dir "trino[sqlalchemy]"`; образ пересобран без кеша. |
| `ModuleNotFoundError: No module named 'trino'` | Trino-драйвер ещё не был установлен в виртуальное окружение приложения | Драйвер установлен в образ Superset; импорт `trino` подтвердил версию `0.340.0`, а подключение через UI прошло Test Connection. |
| Прямой импорт `TrinoEngineSpec` через отдельный `python -c` завершался `App not initialized yet` | Класс импортировался вне инициализированного контекста приложения Superset | Эта диагностическая команда не подтверждает неисправность драйвера. После установки пакета проверка подключения через интерфейс Superset прошла успешно. |
| Superset показывал предупреждение `Using the in-memory storage for tracking rate limits` | Хранилище лимитов запросов не задано, используется память процесса | Для локальной учебной среды предупреждение некритично. Для постоянного многопользовательского/производственного развёртывания следует настроить отдельное хранилище лимитов, например Redis. |
| Docker испытывал повышенную нагрузку во время обработки `lineitem` | Это крупнейшая таблица TPC-H (`sf1`, около 6 млн строк) | Работа выполняется локально в одном стеке; Parquet/ZSTD уменьшают размер хранения и объём чтения, но фактический эффект зависит от машины и числа прогонов. |

&nbsp;

## 8\. Выводы

В проекте реализован медальонный конвейер TPC-H Q10: исходные данные записываются в Bronze, очищаются и фильтруются в Silver, а Gold хранит топ-20 клиентов по выручке от возвращённых товаров. Lakekeeper управляет метаданными Iceberg, PostgreSQL хранит метаданные каталога, файлы Parquet находятся в S3-совместимом хранилище, а Trino выполняет аналитическую обработку. Apache Superset 6.0.0 запущен в Docker, подключение к Trino проверено, а драйвер установлен в виртуальное окружение Superset. В отчёт добавлены инструкции по созданию Dataset, столбчатой диаграммы, KPI-карточки, круговой диаграммы и таблицы, а также по объединению чартов в Dashboard, экспорту его конфигурации и безопасному хранению проекта в GitHub. Эти инструкции описывают дальнейшие действия в интерфейсе; наличие реально созданного и экспортированного дашборда следует подтверждать его сохранением в Superset. `ZSTD` выбран как сбалансированный вариант по скорости и размеру; численные результаты бенчмарка указаны ориентировочно и могут быть заменены фактической медианой нескольких прогонов.
